# Internal voting engine

Approved 23 November 2026. This is an internal allocation component, not an enabled paid-voting flow. Paystack checkout development, webhook intake, provider verification, live processing, email dispatch and refund execution remain paused. No new service is wired into Express or a worker. Existing initialization behavior is preserved.

## Trusted boundary

`VoteAllocationService(database, { provider, environment }, clock).allocate(verificationId)` accepts only the ID of persisted `VerifiedPayment` evidence, never a browser event or an arbitrary `Payment` object. The engine reloads the evidence and purchase under locks. A PAID flag, redirect, payment reference or TypeScript assertion cannot substitute for that record. Authority and TEST/LIVE environment are explicit; there is no environment fallback.

The new evidence table is empty on migration and has **no production writer** in this phase. Database evidence is the trust boundary, not a claim that merely inserting a row performs provider verification. A future separately reviewed server verifier must independently authenticate and verify provider facts, lock competition then payment, validate reference/transaction/amount/currency/environment/timestamps and the original purchase, persist immutable evidence and paid facts atomically, and call this allocator. Never expose evidence creation to browser-facing APIs, ordinary administrator edits, SQL RPCs or a public database role. The migration revokes table and column privileges from PUBLIC and existing Supabase `anon`/`authenticated` roles on VerifiedPayment, VoteAllocation and Contestant, so default grants cannot expose raw totals or permit forged grants. Public clients use Express projections; trusted backend ownership/explicit grants remain. Custom public roles and existing RPCs require deployment review. No hosted permissions are changed or hosted RLS verification claimed by the local tests. Test producers under `apps/api/test` are excluded from the application build and imports.

`VerifiedPayment` records matching reference, provider transaction, integer amount, currency and verified paid/verification timestamps. One record per payment and unique provider/environment/transaction identity prevent reuse. The existing global unique `Payment.providerTxnId` remains intact. PostgreSQL checks evidence against its PAID, non-refunded, scoped purchase and freezes purchase identity, contact and financial snapshot fields after verification. Evidence and original allocations cannot be updated or deleted. Evidence does not allocate votes or change payment status by itself.

`VoteAllocation.verificationId` is nullable only for existing history/legacy writers. No existing allocation is backfilled or recertified. The engine always supplies it, and a composite FK binds it to that same payment. Existing paid/scope/attribution guards and unique payment/allocation identity remain. Direct trusted SQL writes can still create legacy allocations without evidence; that compatibility does not provide a public API, and reconciliation flags those records. Removing this transitional allowance requires a separately reviewed writer cutover. Original allocations must never be overwritten to resolve that flag.

## Allocation and closing policy

The allocator requires completed category setup and integrity cutover, OPEN voting at processing time, verified paidAt inside the current opening-inclusive/closing-exclusive window, no published results, valid immutable PaymentScope, active contestant and matching active ancestors/package, and the same competition/currency throughout. Missing/unscoped legacy records receive no automatic allocation. Invalid or refunded evidence requires review. The purchased vote count and price are the stored administrator-configured purchase snapshot, not today's mutable catalog values. Package deactivation still blocks a new allocation.

Delayed notifications after voting closes go to manual review. This is the conservative internal-phase policy approved with this implementation; the older proposed acceptance of delayed in-window payments is not enabled. Future late-payment policy needs separate review before provider integration.

Lock order is competition, payment, category, subcategory, contestant, package. Competition-first locking serializes with assignment, taxonomy, close and publication; eligibility rows stay locked through commit, including package edits which use their own row lock. This currently serializes all allocations in one competition; throughput tuning is a future measured change, not a reason to weaken integrity.

One Prisma interactive transaction inserts the uniquely keyed allocation, atomically increments the exact BigInt counter and writes `VOTES_ALLOCATED` audit evidence. There is no provider/network call inside it. Allocation, counter, audit or deferred-commit failure rolls all voting effects back. Only confirmed Prisma P2034 transaction conflicts automatically retry, at most twice; other failures propagate. A caller with an unknown commit outcome retries the **same verification ID**. Once committed, replay returns the original allocation without another audit or increment, even after closure/refund/deactivation. This outcome confirms original allocation only; it is not a current payment/refund status or public success receipt. An incompatible legacy allocation is flagged for review instead of adopted.

## Privacy and standings

No public or administrator route can invoke the service, create verification evidence or edit vote totals. Strict contestant DTOs reject `totalVotes`. Existing leaderboards continue filtering the exact competition/category/subcategory before ranking and pagination; there is no global rank. LIVE exposes ranks/totals, RANK_ONLY omits totals, HIDDEN suppresses standings. Setup readiness and existing separately confirmed final publication retain their current behavior. No metadata or public response contains verification/payment evidence.

## Read-only reconciliation and future corrections

`VoteReconciliationService.inspectCompetition(competitionId, { afterId, limit })` reads a repeatable snapshot, using stable contestant-ID pagination (default 50, maximum 100). It reports exact recorded votes, the original allocation sum, their difference, and review flags for unassigned contestants, legacy evidence, unscoped purchases, verified records awaiting allocation, PAID records without evidence and refunded allocations. Inactive contestants are included. It makes no provider calls, processes no events and writes nothing. Reports are internal and must never be returned through public routes.

An allocation sum is not proof that legacy history is complete. A difference is an investigation signal, never permission to reset the counter or manufacture an allocation/baseline. Unknown historical scope remains unknown. A refund status does not silently decrement votes: it produces `REFUND_REVIEW_REQUIRED`. Until a reviewed executor exists, preserve the evidence and escalate to the authorized operator; do not edit original allocation, scope, amount or contact fields.

Future correction contract (design only; no executor or reversal table in this phase):

- Add an append-only `VoteReversal` linked to the original allocation, preserving its original competition/category/subcategory attribution. Give each verified refund/correction event a durable unique key and retain provider/environment/source evidence, reason, actor, timestamps and approved review revision.
- Require a separately authorized, auditable confirmation. A request from a browser or an arbitrary administrator total is never refund proof. Do not move votes between real groups or reinterpret legacy scope.
- Lock competition, payment, original allocation and contestant in the same agreed order. In one Prisma transaction insert the reversal, decrement the counter and write the audit. Database constraints and locked cumulative sums must prevent duplicate reversals, reversal beyond the original grant, and negative totals. Replays return the original reversal. Failures roll everything back.
- Full refunds can reverse only the unreversed original votes. Partial refunds, rounding and disputes require an explicit approved policy; until then they receive review flags and no automatic vote change. Refunded-before-allocation purchases get no allocation. Out-of-order refund evidence must be checked before any grant.
- Published results are locked. Corrections affecting them require a separate reviewed versioning/republishing workflow; never silently change the published table or clear publication. Preserve all original evidence.
- Once implemented, reconciliation compares counters with original allocations minus approved applicable reversals. Repairs need a reviewed explanation for incomplete legacy history and a separate audit record. Never infer revenue from vote totals. Email delivery remains independent.

## Migration and tests

`20261123090000_add_internal_voting_engine` adds empty evidence, a nullable allocation relation, guards and public-role permission revocations. It does not rewrite financial records, counters, taxonomy, publication or any historical migration. Historical allocations become append-only too. Roll out only after reviewing old maintenance/deletion scripts and ensuring a dedicated trusted backend role has its own required privileges rather than relying on PUBLIC grants. This PR applies migrations only to disposable localhost targets; no hosted migration is authorized.

Run `npm run qa:local -- -Phase voting` on Windows with local PostgreSQL 18, or `npm run qa:nonpayment -- voting` with an explicit empty localhost `talenthunt_qa_admin` control database, `QA_DISPOSABLE_DATABASES=1` and `QA_TEST_DATABASE_URL`. The existing runner creates fresh suffixed databases and strips provider/production credentials. The `api` and `all` phases also include the engine and migration suites, including PR CI. Root `npm test` includes the unit guards and retry tests. For direct focused integration use `npm run test:voting --workspace apps/api` with fresh `VOTING_TEST_DATABASE_URL` and empty `VOTING_UPGRADE_TEST_DATABASE_URL` prepared by that runner. There is no DATABASE_URL fallback in financial fixtures.

Tests simulate verified events only in guarded local fixtures, then call the actual service/Prisma/PostgreSQL transaction. They cover duplicates and concurrent payments, invalid identities/ancestry/facts, lifecycle/time boundaries, scope/setup/package/publication gates, failure at every write and deferred commit, retry after commit, BigInt overflow/precision, mutation races, visibility and public/admin write rejection, exact read-only reconciliation, and history-preserving upgrades. The upgrade rehearsal deliberately grants public roles table/column/default privileges first, then verifies SQL reads/writes are denied after migration. Existing non-payment and legacy-history regressions remain active. No test calls Paystack or creates production financial data.

This is a scoped internal slice of #15, with design/reporting groundwork for #17 and tests related to #20. It does not complete their provider, email/outbox, refund or paid-launch acceptance; those issues remain open and payment integration remains paused.
